### T012 - Add Benchmarks And Performance Gates

#### Objective
Add repeatable benchmarks and performance documentation so RawScope can make measured claims about density aggregation, interaction paths, and local ingestion without misleading users.

#### Scope
- Add benchmark infrastructure for CPU reference density, GPU density where locally available, CSV/Parquet ingestion, and evidence export.
- Keep GPU benchmarks opt-in if adapter availability is not reliable in CI.
- Add benchmark datasets or deterministic generators sized for repeatability.
- Update docs with what is measured, what is not measured, and how to run benchmarks.
- Add guardrails so UI titles/logs do not present ad hoc timings as benchmark evidence.

#### Out of Scope
- Do not claim final production performance.
- Do not add benchmark output files as source-controlled truth unless intentionally reviewed.
- Do not add cloud benchmark infrastructure.
- Do not block normal `cargo test --workspace` on GPU availability.
- Do not optimize code unless a separate implementation task is created from benchmark findings.

#### Blocked By
T003, T011

#### Why It Is Blocked
Benchmarks should target the stable generic record model and include the future chunked Parquet path. Measuring synthetic-only or soon-to-be-renamed APIs would create churn.

#### Related Code
- `docs/TECH_DECISIONS.md` - ADR-0010 benchmark before claims and ADR-0015 benchmark timing deferred.
- `crates/rawscope-render/src/density_reference.rs` - CPU density references.
- `crates/rawscope-render/src/gpu_scatter_density.rs` and `gpu_timeline_density.rs` - GPU compute paths.
- `crates/rawscope-data/src/local_dataset/` - CSV and future Parquet loaders.
- `apps/rawscope-workbench/src/demo.rs` - title text must avoid benchmark-like claims.

#### Migration Notes
- Existing tests stay correctness-focused.
- Benchmark output should not be required for normal development.
- Findings can generate future optimization tasks, but this task does not optimize by itself.

#### Misinterpretations To Prevent
- Wrong interpretation: "Add timing to the workbench title."
  Correct rule: benchmark evidence lives in benchmark harnesses/docs, not routine UI.
- Wrong interpretation: "One laptop result proves GPU-scale performance."
  Correct rule: claims must name command, data, hardware, and date.
- Wrong interpretation: "Benchmarks replace correctness tests."
  Correct rule: tests and benchmarks serve different purposes.

#### Invariants
- Normal tests must not require GPU hardware.
- Benchmarks must use deterministic inputs.
- Product docs must avoid unqualified speed/scale claims.
- GPU benchmark paths must be clearly opt-in.

#### Acceptance Criteria
- [ ] CPU density benchmarks exist and run.
- [ ] Data ingestion benchmarks exist for CSV and Parquet after T011.
- [ ] GPU benchmark path is documented as opt-in or skipped with a clear reason.
- [ ] `docs/BENCHMARKS.md` documents commands, assumptions, and claim rules.
- [ ] `cargo test --workspace` still passes without GPU benchmark hardware.

#### Testing Guidance
- Run `cargo test --workspace`.
- Run the CPU benchmark command and record whether it completes.
- Do not require GPU benchmark success unless running on a known compatible machine.
