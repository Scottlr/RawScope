### T007 - Add Egui Workbench Shell

#### Objective
Introduce a small analyst-facing egui/eframe workbench shell that exposes existing RawScope workflows through visible controls, labels, export status, and a row-drilldown panel instead of relying on keyboard shortcuts and window titles.

#### Scope
- Add the first egui/eframe UI integration at the app boundary.
- Preserve existing scatter/timeline WGPU density proof behavior during migration.
- Add visible controls for demo mode, input summary, reset, export, brush status, and selected-row drilldown.
- Add axes/range labels for scatter and timeline views without creating a generic charting system.
- Add tests for UI state formatting and app state transitions where practical.

#### Out of Scope
- Do not build a BI dashboard, layout designer, plugin system, or generic UI framework.
- Do not add Tauri, web, WASM, cloud flows, or remote publishing.
- Do not add Parquet import in this task.
- Do not rewrite GPU compute/render ownership.
- Do not add performance claims.

#### Blocked By
T006

#### Why It Is Blocked
The row-drilldown model should exist before the visible UI panel is built, so UI code displays existing domain state instead of inventing parallel selection logic.

#### Related Code
- `docs/TECH_DECISIONS.md` - ADR-0004 says egui/eframe first when the GUI layer is introduced.
- `apps/rawscope-workbench/src/app.rs` - central state currently coordinated through `winit`.
- `apps/rawscope-workbench/src/app_events.rs` - keyboard and mouse event handling.
- `apps/rawscope-workbench/src/demo.rs` - title formatting that should move toward visible UI state.
- `apps/rawscope-workbench/src/app_render.rs` - render path that must remain owned by WGPU renderers.
- T006 `SelectionDrilldown` - row-drilldown data to display.

#### Implementation Touchpoints
- Read first: ADR-0004/0004A in `docs/TECH_DECISIONS.md`, workbench app modules, T006 drilldown structs, and current `Cargo.toml` dependencies.
- Edit first: root `Cargo.toml` and `apps/rawscope-workbench/Cargo.toml` if adding dependencies to the existing app; create a dedicated UI crate only if the app module split would become a dumping ground.
- Symbols to search: `WorkbenchApp`, `DemoOverlayState`, `TimelineOverlayState`, `event_loop.run_app`, `WindowEvent`, `update_window_title`.
- Required structural changes: add UI state structs, visible control rendering, and a clear boundary between UI state and render state.
- Do not edit: core/data/render APIs unless required by T006 state display.
- Verify in order: `cargo fmt --check`; `cargo check -p rawscope-workbench`; `cargo test -p rawscope-workbench`.
- Stop and ask: if eframe integration conflicts with current direct WGPU surface ownership enough to require a separate technical spike.

#### Implementation Details
- Preferred shape if keeping UI inside workbench:
```text
apps/rawscope-workbench/src/
  ui.rs
  ui_controls.rs
  ui_drilldown.rs
```
- If creating a dedicated crate, use:
```text
crates/rawscope-ui/
  Cargo.toml
  src/lib.rs
  src/workbench_panel.rs
```
and add it to the workspace. Do not create `utils.rs` or `components.rs`.
- Add dependency at the narrowest scope:
```toml
[dependencies]
egui = "..."
eframe = "..."
```
Pin versions intentionally after checking compatibility with current `wgpu = "29.0.3"` and `winit = "0.30.13"`.
- Add UI state types:
```rust
#[derive(Debug, Clone, PartialEq)]
pub struct WorkbenchUiState {
    pub active_view: ActiveView,
    pub dataset_label: String,
    pub view_label: String,
    pub selection_label: String,
    pub export_status: ExportStatus,
    pub drilldown: Option<SelectionDrilldown>,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum ActiveView {
    Scatter,
    Timeline,
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub enum ExportStatus {
    Idle,
    NoSelection,
    Exported { json_path: String, markdown_path: String },
    Failed { message: String },
}
```
- Do not duplicate title-formatting logic. Either replace `DemoOverlayState`/`TimelineOverlayState` with UI-state formatting or make title strings a thin projection of `WorkbenchUiState`.
- Visible controls should include:
  - active view selector;
  - dataset/source label;
  - reset button;
  - export button;
  - current brush/selection summary;
  - row-drilldown table using T006 rows;
  - compact x/y or time/lane axis labels.
- Avoid in-app instructional text that describes keyboard shortcuts. Controls should be discoverable by labels/icons/tooltips once the UI exists.

#### Before / After
**Before:**
```rust
window.set_title(&overlay.title());
```

**After:**
```rust
let ui_state = self.ui_state();
window.set_title(&ui_state.window_title());
```
and a visible egui panel renders the same state.

#### Migration Notes
- This task may be a larger integration if eframe owns the event loop. Keep the first PR focused on the smallest working shell.
- Existing keyboard shortcuts may remain during transition.
- Direct WGPU renderers must still own density drawing.

#### Misinterpretations To Prevent
- Wrong interpretation: "Build a landing page or marketing UI."
  Correct rule: first screen must be the usable workbench.
- Wrong interpretation: "Build a dashboard builder."
  Correct rule: expose current RawScope exploration controls only.
- Wrong interpretation: "Move domain logic into UI code."
  Correct rule: UI adapts existing data/render/workbench state.

#### Invariants
- RawScope remains local-first.
- UI does not claim benchmarked performance or final report support.
- UI state does not duplicate selection/evidence computation.
- Direct render paths remain testable and domain-owned.

#### Acceptance Criteria
- [ ] Workbench has visible controls for active view, reset, export, selection summary, and drilldown.
- [ ] Scatter and timeline views still render existing density paths.
- [ ] Evidence export still writes JSON/Markdown and manifest entries.
- [ ] Row-drilldown panel displays T006 rows without logging raw row values.
- [ ] `cargo check -p rawscope-workbench` passes.

#### Testing Guidance
- Add unit tests for UI state formatting and export status transitions.
- Manual visual verification is required for the first egui shell.
- If browser/app screenshot tooling is available, capture desktop and small-window screenshots for overlap checks.

#### Agent Handoff Context
This is where RawScope starts feeling like a tool instead of a proof. Keep it restrained, visible, and task-focused. The UI should reveal the product contract, not broaden it.

## Final Notes

- Recommended implementation order: after T006.
- Unresolved questions: whether to integrate eframe directly in `rawscope-workbench` or add a narrow `rawscope-ui` crate.
- Risks: event-loop churn, dependency mismatch with `wgpu`, and UI scope creep.
- Areas that need human review before implementation: dependency versions and integration shape.
