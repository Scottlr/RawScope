### T008 - Add Linked Selection Contract

#### Objective
Add a shared visual selection/query contract so RawScope can coordinate selections across scatter, timeline, and future data-quality views without turning into a dashboard or query engine.

#### Scope
- Add foundational selection/query state in `rawscope-core` or a narrow render-owned module if core would become too view-specific.
- Represent active view id, selection id, selection geometry, selected row ids, and source dataset identity.
- Let scatter and timeline workbench states publish finalized selections through the shared contract.
- Let views consume shared selected row ids for highlighting or summary comparison where practical.
- Add tests for deterministic selection ids, row-id set ordering, and clear/reset behavior.

#### Out of Scope
- Do not add arbitrary crossfilter dashboards.
- Do not add SQL/DataFusion or query planning.
- Do not add more than scatter/timeline consumers in the first task.
- Do not add GPU selection masks yet.
- Do not add missingness heatmap implementation; that belongs to T009.

#### Blocked By
T006, T007

#### Why It Is Blocked
The visible UI and CPU-backed drilldown should exist before linking views, otherwise linked selection has no stable user-facing state or row evidence surface.

#### Implementation Details
- In `crates/rawscope-core/src/selection.rs`, extend without pulling in data/render:
```rust
use crate::{F32Range, RowId, U64Range};

#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub struct ViewId(pub u64);

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum VisualSelectionKind {
    ScatterRect,
    TimelineRect,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct CoreLaneRange {
    pub start: u32,
    pub end_exclusive: u32,
}

#[derive(Debug, Clone, PartialEq)]
pub enum VisualSelectionGeometry {
    ScatterRect { x_range: F32Range, y_range: F32Range },
    TimelineRect { time_range: U64Range, lane_range: CoreLaneRange },
}

#[derive(Debug, Clone, PartialEq)]
pub struct VisualSelection {
    pub selection_id: SelectionId,
    pub source_view_id: ViewId,
    pub kind: VisualSelectionKind,
    pub geometry: VisualSelectionGeometry,
    pub selected_row_ids: Vec<RowId>,
}
```
- Add constructors that sort/deduplicate row ids:
```rust
impl VisualSelection {
    pub fn new(
        selection_id: SelectionId,
        source_view_id: ViewId,
        kind: VisualSelectionKind,
        geometry: VisualSelectionGeometry,
        selected_row_ids: Vec<RowId>,
    ) -> Self;
}
```
- In workbench state, add:
```rust
pub(crate) active_selection: Option<VisualSelection>,
pub(crate) next_selection_id: u64,
```
- When scatter/timeline brush finalizes, collect selected row ids from CPU records and publish a `VisualSelection`.
- When a brush clears or dataset changes, clear `active_selection`.
- Future highlighting can remain minimal: show linked selection counts in UI and ensure row ids are available to views.

#### Migration Notes
- `TimelineLaneRange` may stay in render and convert to `CoreLaneRange`.
- Existing brush structs remain valid; linked selection is a higher-level app contract.
- If row-id vectors are large, T012 benchmarks should later measure memory costs.

#### Misinterpretations To Prevent
- Wrong interpretation: "Build crossfilter dashboards."
  Correct rule: this task only publishes one active visual selection contract.
- Wrong interpretation: "Move render brush geometry into core wholesale."
  Correct rule: core gets only dependency-free shared selection geometry.
- Wrong interpretation: "Use unsorted row ids."
  Correct rule: row ids must be sorted and deduplicated for deterministic evidence.

#### Invariants
- Linked selection state must clear on dataset change.
- Selected row ids must be deterministic for the same selection.
- Core must not depend on data, render, GPU, UI, serde, or egui.
- The first linked selection contract handles one active selection, not arbitrary dashboard state.
