### T008 - Add Filter-Aware GPU Density And Filter Shelf

#### Objective

Connect deterministic local-data filters to the real GPU density path and a
bounded workbench filter shelf. Every visible density, count, marginal,
selection, and later inspection must refer to the same active row cohort.

#### Scope

- Add filter catalog/set/evaluation state to scatter workbench coordination in
  a new `app_scatter_filter.rs` module.
- Extend T007 resident state with a revisioned u32 row-mask buffer.
- Update scatter density WGSL to skip excluded rows before binning.
- Create `apps/rawscope-workbench/src/ui_filters.rs` with range and category
  controls ordered by T005 profile hints.
- Add active filter chips, included/total count, clear one/all, and explicit
  include-missing controls.
- Recompute filtered density, marginals, comparison baseline, selection state,
  and inspection prerequisites when filter revision changes.
- Keep full dataset as the baseline and active mask as the visible cohort.
- Make brush selection operate on currently included points only.

#### Out Of Scope

- No arbitrary query builder, OR groups, text contains/regex, saved filter
  presets, remote pushdown, or Parquet predicate pushdown.
- No brush-to-filter Focus action unless it can be implemented as an exact x/y
  numeric filter without broadening scope; otherwise defer it explicitly.
- No difference-density presentation; T012 consumes baseline/active buffers.
- No evidence serialization; T015 owns v4.

#### Blocked By

T004, T006, T007, and T017.

#### Why It Is Blocked

The filter shelf needs explicit interaction state, validated CPU predicates,
resident GPU buffers that can accept mask revisions cheaply, and the final
interactive scheduler so filtered updates do not restore pointer-time work.

#### Implementation Details

Create app state:

```rust
#[derive(Debug, Clone)]
pub(crate) struct ScatterFilterState {
    pub(crate) catalog: Option<rawscope_data::VisualFieldCatalog>,
    pub(crate) filters: rawscope_data::FilterSet,
    pub(crate) evaluation: Option<rawscope_data::FilterEvaluation>,
    pub(crate) last_uploaded_revision: rawscope_data::FilterRevision,
    pub(crate) error: Option<String>,
}
```

Initialize the catalog/evaluation after local source rows load. Synthetic
scatter has no filter shelf in this task. Dataset replacement clears filter
state before building the new catalog.

GPU state adds:

```rust
filter_mask_buffer: wgpu::Buffer,
filter_revision: FilterRevision,
```

Upload one u32 per point only when revision changes. Assert mask length equals
point count before queue writes. The compute shader binding is read-only:

```wgsl
@group(0) @binding(4)
var<storage, read> filter_mask: array<u32>;

if (filter_mask[point_index] == 0u) {
    return;
}
```

Binding 4 follows T007's explicit `0=points`, `1=params`, `2=counts`, and
`3=max_count` scatter layout.

The all-rows state still uploads or binds a valid all-ones mask; do not add a
shader branch based on an absent binding. T007 may initialize this mask.

Add masked render helpers in focused render/data modules rather than cloning
the point vector:

```rust
pub fn scatter_marginal_summary_masked(
    points: &[ScatterPointRecord],
    mask: &FilterMask,
    x_range: F32Range,
    y_range: F32Range,
    x_bin_count: u32,
    y_bin_count: u32,
) -> Result<ScatterMarginalSummary, MaskAlignmentError>;
```

Add explicit masked functions beside the existing selection/comparison owners:

```rust
pub fn selected_region_summary_masked(
    points: &[ScatterPointRecord],
    mask: &FilterMask,
    selection: ScatterBrushSelection,

pub fn scatter_selection_comparison_masked(
    points: &[ScatterPointRecord],

```

Implement both with zipped iteration and no filtered `Vec` allocation.

Create UI projection types in `ui_filters.rs`:

```rust
pub(crate) enum FilterControlState {
```

Use sliders/range controls for numeric fields and searchable checkbox lists for
categories. The profile's first four available hints are expanded; additional
fields live in an Add Filter menu. High-cardinality fields show distinct count
and search only retained catalog values. Never label a truncated catalog as
complete.

Apply filter actions once per egui frame, evaluate once, upload once, clear any
selection containing now-excluded rows, and schedule one exact settled update
through T017. Rebuild comparison/marginals only for that settled mask/viewport
revision. If evaluation fails, retain the last valid mask and show a concise
error; do not display a partially applied cohort.

#### Before / After

**Before:**

```wgsl
let point = points[point_index];
atomicAdd(&counts[bin_index], 1u);
```

**After:**

```wgsl
if (filter_mask[point_index] == 0u) { return; }
let point = points[point_index];
atomicAdd(&counts[bin_index], 1u);
```

#### Migration Notes

- Existing unfiltered behavior uses an all-ones mask and must remain identical.
- No CLI changes; filters are interactive session state.
- Existing v1/v2/v3 evidence remains unfiltered legacy behavior until T015
  adds explicit v4. Do not silently serialize filtered counts into an old shape.
- While any filter is active before T015 lands, set `can_export` to false and
  expose `ExportStatus::Unavailable { reason }` with reason
  `Filtered export requires scatter evidence v4`. T015 removes this temporary
  gate when v4 becomes the default. Unfiltered legacy export remains enabled.

#### Misinterpretations To Prevent

- Wrong interpretation: filter only the fragment shader.
  Correct rule: filter before GPU binning and align CPU summaries/selections.
- Wrong interpretation: rebuild a compact point vector per filter change.
  Correct rule: preserve row alignment through a mask.
- Wrong interpretation: keep selection rows that are excluded by a new filter.
  Correct rule: clear or recompute selection deterministically.
- Wrong interpretation: expose every source column as an expanded control.
  Correct rule: profile-prioritized bounded shelf plus Add Filter menu.

#### Invariants

- CPU included count equals GPU total binned count for the visible viewport
  after accounting for out-of-viewport rows.
- Mask length and point length always match.
- Every summary/selection uses the same mask revision as density.
- Full dataset remains the comparison baseline.
- Invalid actions do not replace the last valid cohort.
- Filter changes do not reupload point coordinates or recreate pipelines.

#### Acceptance Criteria

- [x] All-ones mask reproduces existing density exactly.

## Final Notes

- Recommended implementation order: GPU binding/test, masked CPU summaries,
  app state, UI actions, error handling, native Lichess acceptance.
- Unresolved questions: whether old export is disabled or explicitly marked
  unsupported while filters are active before T015.
- Risks: stale mask revisions, selection mismatch, high-cardinality UI cost.
- Human review: profile field ordering and active-filter visual prominence.
- Completion: implemented on `codex/t008-filter-aware-density`; revisioned
  all-ones/active row masks now feed binding 4 of the resident scatter compute
  path, and the real inspector exposes a bounded profile-ordered filter shelf.
- Architectural decisions: `rawscope-data` remains the predicate/catalog owner,
  `rawscope-render` owns GPU mask resources and allocation-free masked summary
  helpers, and the workbench owns action/evaluation/revision coordination. Full
  rows remain the comparison baseline while visible summaries and drilldown use
  the active cohort. Legacy evidence is disabled with the required v4 reason.
- Validation: six data-filter tests, the complete render and workbench suites,
  four masked API tests, all eight adapter-backed scatter tests,
  `cargo fmt --all --check`, and `cargo check --workspace` passed. Native
  acceptance loaded 200,000 Lichess rows on AMD Radeon RX 7800 XT via Vulkan;
  excluding black wins produced 105,501 rows, excluding Classical games
  produced 174,802 rows, both changed the exact GPU field, and clear-all
  restored 200,000 rows.
- Not run: no screenshot/window/startup tests, benchmark, or timing assertion
  was added or run because these are explicitly outside this task.
- Remaining risk: high-cardinality catalogs still retain up to the data-owned
  catalog limit for search, but each frame renders at most 64 matching options.
  T009/T010/T012/T015 must consume the exposed filter revision and settled mask.
