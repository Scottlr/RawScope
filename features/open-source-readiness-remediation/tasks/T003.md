### T003 — Add Required CI And Platform Gates

#### Objective

Turn the repository's declared quality, packaging, policy, and support contracts
into required, reproducible merge gates while keeping hardware GPU checks
separate and honest.

#### Scope

- Primary audit findings: RS-003, RS-009, and RS-132.
- Add pinned GitHub Actions workflows for Rust quality, supported-platform
  compilation/tests, Python 3.10+ contracts and packaging, Cargo packaging, and
  cargo-deny.
- Add a public platform/backend support matrix based only on runners actually
  validated by the workflow.
- Add deterministic CPU/WGSL parity checks to required CI and a clearly opt-in
  or scheduled adapter-backed GPU job that records adapter/backend metadata.
- Configure dependency caching with lockfile/toolchain keys and least required
  permissions.

#### Out of Scope

- Do not make ignored GPU tests required on generic hosted runners without a
  declared reliable adapter/backend.
- Do not claim Linux/macOS product support merely because `cargo check` passes.
- Do not publish artifacts; T035 owns release workflows.
- Do not duplicate toolchain/lint/advisory policy from T002.

#### Blocked By

T001, T002.

#### Why It Is Blocked

CI must consume approved licences/package metadata and one local toolchain/
policy contract. Creating workflows before those tasks would encode moving or
currently failing gates.

#### Related Code

- Missing `.github/workflows/` directory.
- `rust-toolchain.toml`, `deny.toml`, and manifests established by T001/T002.
- Rust integration tests under `crates/*/tests/` and workbench source tests.
- `crates/rawscope-render/tests/gpu_scatter_density.rs` and
  `gpu_timeline_density.rs` ignored adapter-backed tests.
- `sdk/python/tests/`, `sdk/python/pyproject.toml`, and public setup docs.

#### Implementation Touchpoints

- Read first: T001/T002 handoffs, current GitHub default-branch protection,
  supported runner images, and GPU backend availability.
- Edit first: `.github/workflows/ci.yml`, then
  `.github/workflows/gpu-correctness.yml`, then `docs/SUPPORT.md`.
- Symbols/keys to search: `cargo fmt`, `cargo clippy`, `RUSTDOCFLAGS`,
  `cargo deny`, `unittest discover`, `--ignored`, and `requires-python`.
- Required structural changes: named jobs with stable branch-protection names;
  action references pinned to commit SHAs and minimal `permissions: contents: read`.
- Do not edit: product code except a directly exposed platform failure found by
  a declared matrix; stop and split that fix into its owning task.
- Verify in order: workflow syntax, local equivalence commands, then actual CI
  on a pull request before making checks required.
- Stop and ask: before declaring a new supported OS/backend, adding paid/self-
  hosted runners, weakening a gate because current code fails, or changing remote
  branch-protection settings/required checks. Workflow files may land first;
  branch-protection administration is a separately authorized follow-up.

#### Implementation Details

Required merge jobs:

1. `rust-quality`: fmt, workspace all-target/all-feature check, Clippy
   `-D warnings`, Rustdoc `-D warnings`, and normal tests on the pinned stable.
2. `msrv`: compile/test the subset promised by the T002 MSRV contract.
3. `platform-build`: explicit Windows/Linux/macOS tiers; product support wording
   must distinguish tested execution from build-only status.
4. `python-contracts`: Python 3.10 through the approved upper version, installing
   the `test` extra and running the existing unittest suite.
5. `package-policy`: Rust packages in dependency order, Python sdist/wheel build
   and archive inspection, and `cargo deny check`.

The separate GPU workflow must be manual/scheduled until a reliable runner is
approved. It records OS, adapter name, backend, driver, and test command in its
job summary. Required CI still runs pure binning/ABI/parity vectors so shader
semantic drift is not wholly opt-out.

Use concurrency cancellation for superseded branch runs, bounded timeouts, and
cache keys including OS, Cargo lock hash, and toolchain. Do not cache build
outputs across incompatible targets.

#### Before / After

Before: no merge gate exists and only one Windows machine has exercised the
workspace.

After: every pull request is held to the repository's exact local policy on a
declared matrix, and hardware-dependent evidence is visible without pretending
generic hosted runners provide production GPU coverage.

#### Migration Notes

- Land workflows before requiring branch protection, observe one successful
  run, then configure required job names.
- Changes needed solely to make another platform compile must remain small and
  be attributed; architectural fixes belong in later task owners.
- Shell-neutral commands go in public docs; PowerShell-specific setup may remain
  as an additional Windows section.

#### Misinterpretations To Prevent

- Wrong: unignore GPU tests on all runners. Correct: required pure parity plus a
  separate adapter-backed job on known hardware.
- Wrong: use floating action tags such as `@v4`. Correct: pin reviewed SHAs.
- Wrong: call a build-only target supported. Correct: publish support tiers and
  limitations precisely.

#### Invariants

- Required job names and local commands stay equivalent.
- CI never logs secrets and has least permissions.
- GPU test output records the adapter/backend when run.
- Packaging/policy gates consume T001/T002 configuration, not duplicate it.

#### Acceptance Criteria

- [ ] Required Rust, MSRV, platform, Python, packaging, and policy jobs pass.
- [ ] Actions are pinned, permissions are minimal, caches are target-safe, and
      jobs have bounded timeouts.
- [ ] `docs/SUPPORT.md` matches actual workflow coverage.
- [ ] Hardware GPU tests have a manual/scheduled workflow and recorded metadata.
- [ ] Stable successful job names are documented for branch protection; remote
      branch-protection is changed only after explicit authorization.

#### Testing Guidance

- The workflow run is the integration proof; do not create local CI simulators.
- Keep normal tests deterministic and service-free.
- If GPU hardware is unavailable, required CI must still exercise documented
  CPU/WGSL boundary vectors; record the hardware job as not yet required.

#### Agent Handoff Context

This task makes later remediation enforceable. It must expose failures rather
than papering over them. T035 may reuse reviewed workflow components for release,
but must not turn merge jobs into publishing jobs.

## Final Notes

- Recommended order: required local-equivalent jobs, platform matrix, Python/
  package policy, GPU workflow, branch protection.
- Human review: support tiers, self-hosted GPU runner, and branch-protection admin.
- Risk: all-target Linux dependencies may surface new advisories after T002.
