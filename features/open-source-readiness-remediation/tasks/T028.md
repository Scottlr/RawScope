### T028 — Admit Dataset Generations Under Resource Budgets

#### Objective

Add explicit generation-owned RAM/VRAM accounting and admit a prepared dataset
only when the complete active-plus-pending resource plan fits approved budgets,
preserving the prior active generation on rejection or preparation failure.

#### Scope

- Primary audit finding: RS-115.
- Extend T043's current startup/replacement lifecycle with a typed
  `DatasetResourcePlan` and an atomic `PendingDatasetGeneration` admission step.
- Account store chunks, retained raw values, indexes, projections, selections,
  CPU caches, shared GPU point/event buffers, masks, fields, transition/relief
  resources, readback staging, and required alignment/capacity overhead.
- Include simultaneously live active, pending, and backend-retiring generations;
  never quote only the eventual steady-state footprint.
- Define named RAM/VRAM/queue/cache budgets with units and a typed
  admit/reject/approved-degrade decision.
- Prepare a complete generation off to the side and swap it only after CPU/GPU
  resources and invariants validate; failure/rejection leaves active usable.
- Surface structured budget breakdown and recovery guidance without logging local
  paths or large payloads.

#### Out of Scope

- Do not move startup/GPU initialization off-thread again; T043 already owns that.
- Do not implement final gesture settling or controller restructuring; T029/T050.
- Do not spill to disk, silently sample source truth, or discard evidence-required
  raw values to make a budget pass.
- Do not make default budget choices from unreviewed benchmark results; T057
  measures interactive resource behavior.
- Do not claim driver-resident VRAM; report RawScope-accounted allocations.

#### Blocked By

T006, T009, T022, T025, T043.

#### Why It Is Blocked

Admission needs a typed store/chunk model, bounded ingestion, validated GPU plans,
shared scatter ownership, and a nonblocking active-versus-transition lifecycle.

#### Related Code

- T043 `CurrentStartupState` active/transition lifecycle.
- Dataset store/chunks/indexes/projections and current memory estimates.
- Scatter/timeline GPU states, transitions, readback staging, and WGPU limits.
- UI loading/error/status fields and configuration ownership.

#### Implementation Touchpoints

- Read first: every retained allocation/capacity in data/analysis/render/workbench,
  active/pending overlap, allocator alignment, and current replacement cleanup.
- Edit first: focused resource quantity/budget/plan types near dataset lifecycle,
  then wire estimates from each owning subsystem and add atomic admission.
- Symbols to search: `capacity`, `size_of`, `create_buffer`, `buffer_size`, old/new
  generations, transition resources, caches, staging, and memory estimates.
- Required structural changes: each domain reports its own immutable resource
  estimate; one admission aggregate combines them without moving ownership.
- Do not edit: evidence wire schemas, benchmark claims, controller layout, or
  source semantics.
- Verify in order: checked arithmetic/resource breakdown tests, admission matrix,
  failure/cleanup/old-state tests, focused lifecycle tests, format, workspace.
- Stop and ask: before choosing default budgets or approving any degradation that
  changes exact analysis/evidence truth.

#### Implementation Details

```rust
pub struct ResourceBudgets {
    pub max_ram_bytes: NonZeroU64,
    pub max_accounted_vram_bytes: NonZeroU64,
    pub max_pending_generations: NonZeroU8,
}

pub struct DatasetResourcePlan {
    pub active: ResourceBreakdown,
    pub pending: ResourceBreakdown,
    pub retiring: ResourceBreakdown,
    pub peak: ResourceTotals,
}

pub enum AdmissionDecision {
    Admit,
    AdmitWith(ApprovedPresentationDegradation),
    Reject(ResourceBudgetError),
}
```

All byte/count arithmetic is checked and reports the owning component, requested
bytes, allowed bytes, and units. Capacity, padding, double buffering, and shared
versus unique allocations are explicit so shared point buffers are counted once
and active/pending field slots are counted concurrently.

Approved degradation may reduce preview-only quality, disable a compatible
transition, or evict recomputable presentation caches. It may not alter source
rows, exact cohort/selection/evidence, or silently truncate. The policy is an enum
with documented order; no opportunistic catch-all freeing.

Admission reserves the pending budget before GPU allocation. A prepared generation
is validated and committed with one owner-thread transition; on failure, release
only pending resources and reservation. Backend-retiring resources remain charged
until T023/T058 confirm safe retirement.

#### Before / After

Before: loading can retain multiple whole representations and GPU generations
without a complete peak budget or atomic admission decision.

After: every generation has a checked resource plan, peak overlap is visible, and
only a fully prepared within-policy generation replaces active state.

#### Migration Notes

- Add accounting to the T043 lifecycle without changing its responsiveness or
  stale-completion behavior.
- Initial startup rejection becomes a retryable failed transition; replacement
  rejection preserves prior active state.
- T050 later moves this lifecycle into the dataset controller unchanged.

#### Misinterpretations To Prevent

- Wrong: compare only pending size to the budget. Correct: include all concurrently
  live active/pending/retiring resources.
- Wrong: use `Vec::len()` as RAM. Correct: account retained capacity and owned
  payloads according to documented methodology.
- Wrong: lower exact sample/source truth automatically. Correct: only explicitly
  approved presentation degradation is permitted.

#### Invariants

- Every admitted generation has a complete checked resource breakdown.
- Peak admission includes all concurrently live generations/resources.
- Budget failure cannot clear or partially mutate active state.
- Pending/retiring resource reservations are released exactly once.
- Reported VRAM is labelled as RawScope-accounted allocation, not driver residency.

#### Acceptance Criteria

- [ ] Typed budgets/plans account every named RAM/VRAM owner and checked overhead.
- [ ] Shared resources are counted once and active/pending/retiring overlap is
      included in peak totals.
- [ ] Admit/reject/approved-degrade policy is explicit and truth-preserving.
- [ ] Replacement rejection/failure preserves active state and cleans pending
      reservations/resources exactly once.
- [ ] Focused accounting/admission/lifecycle tests, format, and workspace checks pass.

#### Testing Guidance

- Use table-driven exact-boundary, one-byte-over, overflow, shared-allocation,
  double-buffer, cancellation, and replacement-failure cases.
- Inject resource builders; assert ownership/cleanup rather than allocator timing.
- No large synthetic smoke load or diagnostic memory script.

#### Agent Handoff Context

T029 consumes admitted generations in final settling. T050 moves lifecycle
ownership; T057 later measures and informs human-approved defaults.

## Final Notes

- Recommended order: quantity types, owner estimates, aggregate/admission policy,
  lifecycle reservation/commit, cleanup tests.
- Human review: default budgets and permitted presentation degradations.
- Risk: WGPU internal allocations remain unobservable; keep claims to accounted
  RawScope resources and preserve conservative overhead assumptions.
