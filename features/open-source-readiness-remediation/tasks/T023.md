### T023 — Add Cancellable Nonblocking GPU Readback

#### Objective

Replace indefinite device polling and misleading async functions with a real
callback-driven readback state machine that supports bounded progress, timeout,
cancellation, recovery, and explicit result ownership without blocking the UI.

#### Scope

- Primary audit findings: RS-049, RS-051, and RS-052.
- Add a low-level `GpuReadbackTicket`/state machine that retains staging buffers
  until WGPU map completion and reports ready/error/cancelled/timeout outcomes.
- Remove `PollType::wait_indefinitely()` and synchronous channel receive from all
  display/interaction paths.
- Replace fake `pub async fn` GPU APIs with synchronous start/submit functions plus
  completion polling, or a truly yielding future backed by the same state machine;
  public semantics must be honest.
- Integrate device-loss/recovery cancellation from T058 and expose generation IDs
  so stale results can be discarded by T027/T029.
- Clear reusable GPU buffers through encoder `clear_buffer` or a bounded backend-
  justified path, not a newly allocated/uploaded full zero vector per update.

#### Out of Scope

- Do not add a Tokio runtime, detached threads, busy polling, or sleeps.
- Do not decide workbench job/coalescing policy; T027/T029 own orchestration.
- Do not force readback for display normalization where GPU-resident reductions
  suffice.
- Do not delete explicit full-readback correctness APIs/tests.

#### Blocked By

T022, T058.

#### Why It Is Blocked

Tickets require T022's validated buffer lengths and T058's structured WGPU
errors/device-generation recovery signals before cancellation and stale-result
handling are safe.

#### Related Code

- `crates/rawscope-render/src/gpu_density_pipeline.rs::readback_counts_from_buffer`.
- `gpu_scatter_density.rs`/`gpu_timeline_density.rs` public async functions.
- `scatter_density_gpu_state.rs` explicit readback policies.
- WGPU device polling in workbench render/event loop.

#### Implementation Touchpoints

- Read first: locked WGPU 29 map callback/poll APIs, staging-buffer lifetimes,
  every call to `device.poll`, channel receive, and readback policy.
- Edit first: a focused low-level readback module, then scatter/timeline wrappers
  and buffer-clearing paths.
- Symbols to search: `wait_indefinitely`, `mpsc`, `map_async`, `recv`,
  `pub async fn gpu_`, zero-vector allocation, and `write_buffer` clears.
- Required structural changes: state enum `Submitted/Mapping/Ready/Failed/
  Cancelled/Taken`; result can be consumed exactly once.
- Do not edit: gesture scheduler, workbench worker pool, analysis/evidence.
- Verify in order: deterministic state-machine tests, pure length/decode tests,
  adapter-backed success/cancellation/device-error tests, format, workspace check.
- Stop and ask: if the event loop cannot guarantee bounded device polling cadence
  or if timeout ownership belongs at a different approved layer.

#### Implementation Details

Use explicit submission and completion:

```rust
pub struct GpuReadbackTicket<T> {
    generation: GpuJobGeneration,
    staging: wgpu::Buffer,
    state: ReadbackState<T>,
    deadline: Instant,
    completion: Arc<ReadbackCompletionCell>,
}

pub enum ReadbackProgress<'a, T> {
    Pending,
    Ready(&'a T),
    Failed(&'a GpuReadbackError),
    Cancelled,
}
```

The map callback writes its single terminal map result into a per-ticket one-shot
completion cell (`OnceLock`/equivalent) that cannot be lost to a full shared
channel, then asks an injected waker/event-loop proxy to wake the owner. Wake
failure does not discard the durable completion cell. The callback never blocks
or waits for channel capacity.

While any ticket is pending, the application coordinator must request explicit
bounded progress/wake scheduling: use the callback wake plus winit
`ControlFlow::WaitUntil` (or the locked-version equivalent) at a named maximum GPU
progress interval and the nearest ticket deadline. A static window therefore
still invokes nonblocking `device.poll` and advances timeout/completion; do not
depend on incidental input/redraw events. Timeout/cancellation marks a ticket
non-publishable, drops mapped views safely, unmaps when legal, and retains
resources until WGPU no longer references them.

Decode checks exact expected byte/element count before `bytemuck` cast/copy and
unmaps only after the view drops. `take_result()` is one-shot. Full-count readback
remains explicit for settled analytics/tests; normal rendering uses no readback or
small maximum/result buffers.

Use `CommandEncoder::clear_buffer` for reusable count/max buffers where WGPU
guarantees alignment/usage. Any backend fallback zero buffer is allocated once
under a named byte cap.

#### Before / After

Before: map waits indefinitely, async functions block synchronously, and clears
allocate/upload full zero vectors.

After: readback advances through bounded callbacks/events, can be cancelled or
timed out, and reusable buffers clear without per-update host allocation.

#### Migration Notes

- Keep convenience correctness functions by starting a ticket and driving it only
  in test/CLI contexts with an explicit bounded wait; interactive callers never do.
- Rename/remove misleading async APIs in one workspace migration before release.
- T027 owns application job IDs; bridge them to the ticket generation explicitly.

#### Misinterpretations To Prevent

- Wrong: move `wait_indefinitely` to a worker thread. Correct: use callback state
  and bounded device progress/cancellation.
- Wrong: drop the staging buffer on cancellation immediately. Correct: retain it
  until WGPU completion/lifetime rules permit cleanup.
- Wrong: remove full readback tests. Correct: keep explicit correctness paths.
- Wrong: send the sole completion into a shared bounded `try_send` channel and
  ignore `Full`. Correct: store one terminal result durably per ticket, then wake.
- Wrong: poll only on ordinary input/redraw. Correct: pending tickets schedule a
  bounded `WaitUntil`/deadline wake even when the window is otherwise idle.

#### Invariants

- No interactive GPU path blocks indefinitely or synchronously receives mapping.
- Ticket resources outlive all submitted/map use.
- Completion/error is surfaced exactly once with generation context.
- A terminal callback result cannot be lost because a shared queue is full or the
  event-loop wake request is already closed.
- Pending tickets guarantee explicit bounded progress/deadline wake scheduling.
- Timeout/cancellation cannot publish partial counts.
- Normal clears allocate no vector proportional to grid size.

#### Acceptance Criteria

- [ ] No `wait_indefinitely`/blocking receive remains in interactive readback.
- [ ] Public GPU API names/signatures match real synchronous-start/nonblocking-
      completion semantics.
- [ ] Cancellation, timeout, device loss, map error, and success are observable.
- [ ] A static-window test proves pending tickets schedule progress/deadline wakes,
      and a saturated unrelated event queue cannot lose terminal completion.
- [ ] Full-readback correctness paths remain and validate buffer length.
- [ ] Buffer clearing reuses GPU commands/resources.
- [ ] State-machine and adapter-backed tests plus workspace check pass.

#### Testing Guidance

- Unit-test transition ordering with an injected completion source/fake clock;
  never use sleeps.
- Test a closed waker/event-loop proxy: the completion cell still reaches terminal
  state and shutdown cleanup can reap it without publishing to a dead app.
- Adapter tests cover successful readback, cancellation before/after callback, and
  result generation; mark hardware tests consistently with existing suites.
- Assert no host zero allocation via the clear-plan contract, not a flaky allocator
  global.

#### Agent Handoff Context

T024/T025 consume tickets in resident engines. T027 routes completions to winit;
T029 owns coalescing and exact-settle publication.

## Final Notes

- Recommended order: state machine, decode/lifetime, API migration, buffer clears,
  adapter tests.
- Human review: default readback timeout and event-loop polling cadence.
- Risk: cancellation does not necessarily cancel already-submitted GPU work; it
  prevents publication and cleans only when the backend completes safely.
