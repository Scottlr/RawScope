### T043 — Move Current Startup And GPU Initialization Off The Event Thread

#### Objective

Close the Critical startup stall in current architecture: start winit first,
resolve/load data on bounded jobs, request adapter/device without event-thread
`pollster::block_on`, and retain prior ready state through replacement failure.

#### Scope

- Primary audit finding: RS-107.
- Split CLI syntax parsing from bounded session resolution/data preparation.
- Add current lifecycle stages `ResolvingSession`, `InitializingGpu`,
  `LoadingDataset`, `PreparingView`, `Ready`, and persistent `Failed` over a
  separately retained active ready state.
- Drive `request_adapter`/`request_device` futures on an approved non-event-thread
  job or explicit wakeable future state, then configure surface/create presentation
  state on the owning event thread after completion.
- Run current eager data preparation off-thread through T027; T009 may later replace
  internals without changing lifecycle.
- Cancel superseded work and reject stale completion by startup/dataset/device IDs.

#### Out of Scope

- Do not add final RAM/VRAM budgets/generation admission; T028 owns it.
- Do not introduce Tokio, detached threads, or mutate app through a mutex.
- Do not create WGPU presentation resources on an unsupported thread.
- Do not add new loading UI beyond existing status/error projection.

#### Blocked By

T005, T011, T022, T027, T058.

#### Why It Is Blocked

Startup needs checked IDs/session bounds, real jobs, validated GPU plans, and
explicit adapter/recovery policy before stale/failure transitions are safe.

#### Implementation Details

Use:

```rust
pub struct CurrentStartupState {
    active: Option<Arc<CurrentReadyState>>,
    transition: StartupTransition,
}

pub enum StartupTransition {
    Idle,
    ResolvingSession { job: JobHandle },
    InitializingGpu { job: JobHandle, request: ResolvedStartup },
    LoadingDataset { job: JobHandle, gpu: Arc<PreparedGpuContext> },
    PreparingView { prepared: PreparedCurrentView },
    Failed { request: StartupRequest, error: WorkbenchOperationError },
}
```

The adapter/device job returns handles/capabilities/error only; surface configure
and window-bound presentation setup occur on the event thread in a bounded apply
step. If WGPU futures must be polled locally, pending state schedules explicit
wakes/deadlines and never `block_on`. No event-thread `pollster::block_on` remains.

Replacement loading keeps `active` renderable. Every completion matches job +
startup/dataset/device generation before transition. Failure drops only pending
resources, preserves active, and exposes retry.

#### Before / After

Before: manifest/data preparation and GPU initialization can block before/during
the event loop, leaving no responsive failure/retry UI.

After: startup is staged/wakeable/cancellable and active state survives replacement
failure.

#### Migration Notes

- T028 adds final resource accounting/admission to the same lifecycle.
- T050 moves lifecycle into final dataset controller; preserve tests.

#### Misinterpretations To Prevent

- Wrong: move `pollster::block_on` to another event callback. Correct: job/future
  completion wakes the event loop.
- Wrong: send `&mut WorkbenchApp` to worker. Correct: owned input/result.
- Wrong: clear current dataset when replacement begins. Correct: retain active.

#### Invariants

- No session/data IO or `pollster::block_on` blocks the event thread.
- Window/surface-bound work occurs on the allowed owner thread.
- Stale completions cannot advance/replace current state.
- Replacement failure preserves active ready state and pending cleanup.
- Accepted jobs produce visible terminal status.

#### Acceptance Criteria

- [ ] Event loop/window starts before bounded session/data work.
