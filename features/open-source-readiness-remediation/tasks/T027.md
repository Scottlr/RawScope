### T027 — Add A Native Job Coordinator And Typed Operation Errors

#### Objective

Introduce one bounded, shutdown-aware workbench job system with owner-minted IDs,
cancellation, winit completion events, structured tracing, and source-preserving
operation errors; prove it with bounded session-manifest resolution after the
event loop starts, before T028 moves full dataset preparation.

#### Scope

- Primary audit findings: RS-109 and RS-117; foundation for RS-104 and RS-107.
- Add a bounded worker pool/job coordinator appropriate to the native winit app;
  no general async runtime is required.
- Define private `WorkbenchJobId`, job kind/generation, cancellation token,
  coalesced progress events, durable per-job terminal results, queue/backpressure
  behavior, and joined shutdown.
- Create a top-level `WorkbenchOperationError` with typed source variants and
  recovery classification; do not erase domain errors into strings/boxed errors at
  controller boundaries.
- Route completion/failure through a typed winit user event and request redraw.
- Split syntactic CLI request parsing from bounded session-manifest resolution and
  run the latter as the first real job, returning a typed resolved-startup event.
- Replace the current “in-flight” boolean/debounce terminology with actual job
  handles and completion state.

#### Out of Scope

- Do not load/prepare dataset contents or render settling yet; T028/T029 own them.
- Do not move evidence export yet; T049 adopts T021 through a dedicated export
  controller after the evidence transaction API is stable.
- Do not spawn detached threads, add Tokio, use unbounded channels, or hold locks
  across waits/callbacks.
- Do not perform WGPU resource creation/presentation on arbitrary workers.
- Do not log raw evidence, full paths by default, or large payloads.

#### Implementation Details

Use ownership transfer rather than shared mutable app state:

```rust
pub struct JobCoordinator { /* bounded sender, workers, ID clock */ }

pub struct JobHandle {
    id: WorkbenchJobId,
    kind: WorkbenchJobKind,
    cancel: CancellationToken,
}

pub enum WorkbenchUserEvent {
    JobProgress(JobProgress),
    JobCompleted(JobCompletion),
    GpuReadbackReady(GpuReadbackCompletion),
}
```

Jobs receive immutable owned inputs and return owned results/errors. Channel
capacity and maximum live jobs are named configs with units; saturation returns
`JobSubmitError::QueueFull` rather than blocking the event thread. Cancellation is
cooperative at bounded units.

Every accepted job receives a registry entry containing a single-assignment
terminal cell before it enters the queue. Each worker wraps the individual job
closure with `std::panic::catch_unwind(AssertUnwindSafe(...))` (or an equivalently
reviewed boundary), converts panic into a fatal typed `JobError`, and stores one
of success/failure/cancelled/panicked in that cell before attempting notification.
A worker-thread join error alone is too late and cannot identify or terminalize
all accepted work.

Progress is advisory: keep at most the latest progress value per job and allow
progress wake coalescing/dropping under pressure. Terminal completion is not sent
only through the bounded event queue. It remains durably queryable in the job
registry; `EventLoopProxy::send_event` merely wakes the owner. If the proxy is
closed, mark the coordinator closing, reject new admissions, retain terminal
results for shutdown reaping, and do not erase the original outcome.

Shutdown is an explicit state transition: stop admissions, cancel queued/running
jobs, let every accepted job reach a terminal cell, drain/reap results/resources,
close worker channels, and join all workers. A configured bounded grace period
may escalate to a fatal process-level outcome, but must not detach threads or
pretend accepted work completed.

Error hierarchy:

```rust
pub enum WorkbenchOperationError {
    Session(#[source] SessionError),
    Job(#[source] JobError),
}
```

T028-T030 extend this enum with ingestion/analysis/GPU/evidence/bundle variants as
those owners are adopted; they must preserve concrete sources rather than add a
catch-all string/boxed variant. Add `recovery_class()` (`Retryable`,
`ReloadDataset`, `RecreateGpu`, `Fatal`) and structured spans containing job
kind/ID and generation—not sensitive payloads.

Syntactic CLI parsing produces a small `StartupRequest` before the event loop.
The app starts in `ResolvingStartup`, submits bounded manifest IO/validation, and
accepts only the matching `ResolvedStartup` completion. T028 then submits dataset
preparation from that resolved request.

#### Before / After

Before: synchronous work is labelled in-flight, session resolution occurs before
the event loop can report progress/failure, and errors lose types/context.

After: real bounded jobs report typed completion/failure to the event loop and
the first bounded startup operation runs without accessing mutable app state.

#### Migration Notes

- Keep job runtime synchronous internally; it need not expose async Rust APIs.
- App startup constructs the user-event loop/proxy before controllers needing the
  coordinator.
- T028/T029 add job kinds; they must reuse this coordinator, not spawn new pools.

#### Misinterpretations To Prevent

- Wrong: wrap synchronous startup in `async fn` and block_on. Correct: execute
  bounded manifest IO/validation on a worker and deliver a completion event.
- Wrong: use `Arc<Mutex<WorkbenchApp>>` in jobs. Correct: jobs own inputs/results;
  app commits results on its thread.
- Wrong: log every success/payload. Correct: spans/errors carry IDs/generations and
  useful context without noisy or sensitive data.

#### Invariants

- Event-loop submission never blocks on queue capacity or job completion.
- Workers are bounded, named, cancellation-aware, and joined at shutdown.
- Every accepted job produces one terminal completion.
- Terminal state is durable per job even when progress/event queues are saturated
  or the event-loop proxy is closed.
- Mutable workbench state is touched only when handling completion on owner thread.
- Domain errors preserve source and recovery classification.

#### Acceptance Criteria

- [ ] Bounded job coordinator and typed winit user events exist.
- [ ] Queue full/cancel/shutdown/panic/error behavior is deterministic and visible.
- [ ] Each accepted job is wrapped at the per-job panic boundary and reaches one
      durable terminal cell before any wake attempt.
- [ ] Progress coalescing/saturation and a closed event-loop proxy cannot lose a
      terminal result; proxy closure stops new admissions and shutdown reaps it.
- [ ] Shutdown cancels/drains all accepted work and joins every worker.
- [ ] Bounded session resolution runs after event-loop startup and commits only by
      matching job ID.
- [ ] Synchronous scheduler no longer claims work is in-flight.
- [ ] Operation errors preserve domain sources and recovery class.
- [ ] Focused job/startup-resolution/workbench tests and workspace check pass.

#### Testing Guidance

- Use barriers/channels/fake executor hooks, never sleeps, to test ordering,
  saturation, cancellation, stale completion, and joined shutdown.
- Panic one queued job while another succeeds; assert both terminalize and the
  worker accounting remains consistent. Close the event proxy before completion
  and assert the registry still exposes/reaps the exact terminal result.
- Inject bounded session read/parse failure and assert typed completion/UI state.
- No live window or fake service.

#### Agent Handoff Context

T028/T029 build on this one runtime, and T030 later moves T021 export through it.
Keep APIs narrow and task-oriented; this is not a framework.

## Final Notes

- Recommended order: IDs/errors, pool/channels, user event, startup resolution,
  observability, deterministic tests.
- Human review: worker count, queue capacity, shutdown policy, and sensitive log
  fields.
- Risk: event-loop proxy lifetime/shutdown ordering must prevent sends after app
  teardown without dropping an accepted job invisibly.
