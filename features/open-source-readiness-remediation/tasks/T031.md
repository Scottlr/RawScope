### T031 — Add A Deliberate Cargo Feature Matrix

#### Objective

After crate ownership is correct, make genuinely optional build-time capabilities
explicit at their narrow owners so headless/session/data consumers avoid unrelated
Arrow/Parquet, windowing, and surface dependencies without hiding bad dependency
directions.

#### Scope

- Primary audit finding: RS-012.
- Add a small documented feature matrix only for real optional behavior.
- Make Parquet/Arrow ingestion an optional `rawscope-data` feature while retaining
  CSV as the minimal/default supported local adapter; workbench opts into both.
- Separate compute-only `rawscope-gpu` from optional native surface/winit support
  if the final code boundary allows it; workbench opts into `surface`.
- Keep `rawscope-analysis`, session contracts, and evidence free of GPU/UI features
  by dependency direction rather than feature switches.
- Audit default features and direct dependency feature sets for minimality; align
  workspace dependency versions only when multiple crates truly share them.
- Document supported feature combinations and check a bounded meaningful set.

#### Out of Scope

- Do not feature-gate arbitrary modules to reduce compile errors.
- Do not make every dependency optional or test the power set of features.
- Do not create a “headless render” promise if render fundamentally owns WGPU.
- Do not change runtime product behavior for the default workbench build.

#### Blocked By

T001, T003, T011, T019, T022, T030, T058.

#### Why It Is Blocked

Features must follow final crate ownership, and T003 must exist so every documented
combination is made a real gate in the same task. Adding features earlier would
conceal the session/data, render/evidence, and GPU/windowing dependency problems.

#### Related Code

- Root and all package `Cargo.toml` files after new crates are added.
- Arrow/Parquet dependencies in `rawscope-data`.
- `wgpu`/`winit` surface and compute owners in `rawscope-gpu`/workbench.
- `cargo tree -e features` output and package public facades/docs.
- T002 cargo-deny duplicate policy and T003 CI jobs.

#### Implementation Touchpoints

- Read first: `cargo metadata` dependency graph, every optional capability caller,
  dependency default features, and package docs/examples.
- Edit first: narrow owner manifests and `cfg` facade wiring, then workbench
  explicit feature requests, docs, and T003 checks.
- Symbols/keys to search: `[features]`, `default-features`, Arrow/Parquet imports,
  winit surface modules, and unconditional facade re-exports.
- Required structural changes: feature-specific modules remain domain-owned; use
  clear compile errors/docs when an API is unavailable.
- Do not edit: semantic algorithms, evidence/session wire shapes, or public release
  intent.
- Verify in order: minimal/default data build/tests, data with Parquet, GPU compute
  without surface, full workbench all features, cargo tree comparison, format,
  workspace check.
- Stop and ask: if CSV should also be optional, if compute-only GPU is not a real
  supported consumer, or if a feature changes the promised public API/default.

#### Implementation Details

Expected shape, adjusted to final manifests:

```toml
# rawscope-data
[features]
default = ["csv"]
csv = ["dep:csv"]
parquet = ["dep:arrow-array", "dep:arrow-schema", "dep:parquet"]

# rawscope-gpu
[features]
default = []
surface = ["dep:winit"]
```

The native app explicitly requests `rawscope-data` `csv,parquet` and
`rawscope-gpu` `surface`. If render requires compute WGPU, that remains an ordinary
dependency; do not invent a disabled renderer that cannot render.

Guard imports/modules/public exports with the owning feature and document error/
availability. Avoid public types containing optional-dependency types when the
feature is disabled. Use `cargo tree -e features` before/after to explain direct
build graph changes; do not claim speed/size without T033 measurement.

T003 adds a bounded matrix: minimal defaults, each meaningful optional feature,
and full workbench. Do not test nonsensical combinations.

#### Before / After

Before: session/data consumers build Arrow/Parquet and GPU/windowing costs travel
through unrelated dependencies.

After: optional capabilities compile only when requested, while default workbench
behavior remains unchanged and foundational crates need no feature hacks.

#### Migration Notes

- Feature names are public package API; document them before T035.
- Preserve default app functionality by explicitly opting in at the app manifest.
- Lockfile changes must be attributable and rechecked by cargo-deny.

#### Misinterpretations To Prevent

- Wrong: put a `serde` feature on core. Correct: core stays dependency-free and
  wire crates adapt its types.
- Wrong: feature-gate evidence out of render while keeping the dependency cycle.
  Correct: T019 removes the ownership problem first.
- Wrong: call a smaller cargo tree a performance result. Correct: record graph
  change; T033 measures build/runtime resources.

#### Invariants

- Features represent real compile-time capabilities with documented consumers.
- Default native workbench retains CSV/Parquet/GPU surface behavior.
- Foundational crates remain free of unrelated optional dependencies by direction.
- No feature cycle or public optional-dependency type leakage.
- CI covers only meaningful supported combinations.

#### Acceptance Criteria

- [ ] Parquet/Arrow and optional surface/window dependencies are narrowly gated
      where final architecture supports it.
- [ ] Minimal/default and full workbench configurations compile/test.
- [ ] Feature docs and CI matrix match actual supported combinations.
- [ ] `cargo tree -e features` shows unrelated consumers no longer pull heavy roots.
- [ ] Default app behavior and workspace checks remain intact.

#### Testing Guidance

- Use Cargo check/test per meaningful feature combination; no fake consumer app.
- Add compile-time facade tests only when they protect a public feature contract.
- Do not add broad `cfg` test duplication or benchmarking here.

#### Agent Handoff Context

T034 documents final package/API boundaries; T035 packages only approved feature
sets. Keep the matrix small enough for contributors/CI to understand.

## Final Notes

- Recommended order: dependency graph audit, data features, GPU surface feature,
  facade guards, app opt-ins, docs/CI.
- Human review: minimal defaults and whether compute-only GPU is supported.
- Risk: optional dependency types can leak into public signatures and make minimal
  builds fail; inspect `cargo doc/check` for each documented combination.
