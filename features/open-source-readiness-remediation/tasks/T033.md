### T033 — Add Reproducible CPU Product Benchmarks

#### Objective

Replace unsafe or unrepresentative benchmark coverage with reproducible CPU-side
product-path scenarios for ingestion, indexing, selection, evidence, and bundle
creation, each carrying enough metadata to support only truthful reviewed claims.

#### Scope

- Primary audit finding: RS-143.
- Define a versioned benchmark-result metadata contract containing command,
  scenario/fixture version, dataset characteristics, feature set, commit/dirty
  state, OS/CPU/RAM, Rust/toolchain version, date, samples, and metric units.
- Benchmark real CSV/Parquet ingestion into `DatasetStore`, chunk/index/profile
  construction, cohort/selection/inspection, canonical evidence formatting, and
  transactional local bundle creation through public product seams.
- Separate cold preparation, incremental update, and steady-state query metrics;
  do not join incompatible histories under one benchmark name.
- Repair current fixture cleanup with owned temporary directories/RAII and remove
  any dead or dangerous path-manipulation cleanup.
- Record peak/retained RAM estimates only through T028's documented accounted
  resource model and label them accordingly.
- Document the exact invocation/result-review protocol without committing large
  current-user datasets or unreviewed headline baselines.

#### Out of Scope

- Do not benchmark interactive GPU, gesture/settle, relief, VRAM, or device
  generations; T057 owns those hardware-bound scenarios.
- Do not change defaults or README scale claims from one unreviewed run.
- Do not create a diagnostic benchmark script, fake app, or one-off dry run.
- Do not treat benchmark compilation as performance evidence.
- Do not commit private/local datasets or absolute paths.

#### Blocked By

T009, T012, T015, T021, T032.

#### Why It Is Blocked

Benchmarks must exercise final bounded ingestion/index/evidence paths and rely on
the atomicity suite so measured scenarios cannot silently produce invalid state.

#### Related Code

- Existing Criterion benches and any fixture/temp cleanup helpers.
- Final data/store/analysis/evidence public APIs and Python preparation seam.
- T028 resource accounting contract and current performance claims/docs.
- Existing deterministic/synthetic datasets suitable for committed fixtures.

#### Implementation Touchpoints

- Read first: every benchmark target, actual product call path, fixture ownership,
  cleanup, current claim, and Criterion configuration.
- Edit first: metadata/scenario support in the bench harness, repair RAII fixtures,
  then add narrowly versioned product scenarios.
- Symbols to search: `criterion_group`, temporary paths, recursive cleanup,
  synthetic sizes, direct helper bypasses, throughput, and README claims.
- Required structural changes: shared benchmark fixture module only within the
  existing benches pattern; no production benchmark API unless product already
  needs the seam.
- Do not edit: GPU pipelines, release workflow, default product budgets, or claims.
- Verify in order: benchmark target compilation, fixture lifecycle tests if they
  protect path safety, one explicitly approved contextualized run when requested,
  format, workspace check.
- Stop and ask: before running/committing a large baseline or selecting datasets/
  thresholds intended to gate release claims.

#### Implementation Details

Scenario IDs encode semantics, not marketing size labels. A result record includes
the command and complete context; dirty worktree results are marked exploratory
and cannot support release claims.

Use deterministic generated fixtures with documented distributions and small
committed edge fixtures. Each benchmark calls the same loader/store/index/
selection/evidence/bundle seam used by the product. Bundle benchmarks own a
temporary root through RAII and verify setup/teardown containment before timing;
timing excludes fixture generation only when stated.

Report latency/throughput distributions appropriate to the harness and keep cold
versus warm/incremental measurements separate. Accounted RAM is an auxiliary
metric with method/version, never presented as process RSS or driver residency.

#### Before / After

Before: benchmark fixtures can be unsafe, important product paths are absent, and
results lack context needed for a defensible claim.

After: maintained CPU scenarios are reproducible, contained, product-realistic,
and labelled with sufficient provenance for human review.

#### Migration Notes

- Preserve a current benchmark name only if scenario semantics remain comparable;
  otherwise version/rename it.
- External flagship datasets remain an optional human-run input and are not
  committed.
- T052 may cite results only after the documented protocol and human review.

#### Misinterpretations To Prevent

- Wrong: a compiled benchmark validates performance. Correct: only a contextual
  run yields performance evidence.
- Wrong: benchmark a helper the product bypasses. Correct: invoke public seams.
- Wrong: call accounted allocations RSS. Correct: label metric/method exactly.

#### Invariants

- Every result names scenario, command, dataset, platform, date, commit, and units.
- Fixtures cannot delete outside their owned temporary root.
- Cold/incremental/steady-state results are never combined ambiguously.
- No scale/default claim changes solely from unreviewed output.
- CPU task contains no GPU/interactive benchmark scope.

#### Acceptance Criteria

- [ ] Real ingest, index/profile, selection/inspection, evidence, and bundle paths
      have maintained versioned scenarios.
- [ ] Result metadata and units are complete enough to reproduce/review a run.
- [ ] Fixture creation/cleanup is RAII-contained and dangerous dead cleanup removed.
- [ ] Cold/incremental/steady-state semantics are explicit and comparable histories
      are preserved or versioned.
- [ ] Benchmark targets compile and relevant workspace checks pass.

#### Testing Guidance

- Benchmarks are not correctness tests; rely on T032 and fail setup if generation/
  output invariants are invalid.
- Add a focused unit test only for metadata validation or cleanup containment where
  it prevents a realistic reporting/filesystem regression.
- Do not run or commit large baselines without explicit request and context.

#### Agent Handoff Context

T057 adds hardware-bound interactive metrics. T052 reconciles claims only after
both protocols yield reviewed evidence.

## Final Notes

- Recommended order: metadata contract, fixture safety, ingest/index scenarios,
  selection/evidence/bundle scenarios, protocol docs.
- Human review: dataset matrix, run environment, claim thresholds, and baselines.
- Risk: Criterion throughput and end-to-end latency answer different questions;
  keep them separately named and interpreted.
