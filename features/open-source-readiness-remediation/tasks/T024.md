### T024 — Build A Resident Timeline Engine

#### Objective

Turn the tactically corrected timeline path into a resident GPU engine that
uploads dataset events once, reuses validated resources, and exposes nonblocking
preview/exact generations without reimplementing lane or range semantics.

#### Scope

- Primary audit finding: RS-050.
- Add `TimelineDensityGpuState` keyed by dataset and device generation, retaining
  event buffers, pipelines/layouts, parameter buffers, double count/max fields,
  render bindings, and T023 readback tickets.
- Upload event data only when the dataset/device generation changes; viewport,
  cohort, and encoding updates reuse resident capacity and cached bindings.
- Consume T037's lane-orientation, timestamp-range, empty-config, and before/after
  contract unchanged in CPU packing, WGSL, render sampling, axes, and hit testing.
- Expose explicit preview and exact field generations; interactive preview may
  remain GPU-resident while exact completion uses a bounded ticket when required.
- Validate all resource plans through T022 and retire resources only after WGPU
  and ticket lifetimes permit.

#### Out of Scope

- Do not refix or redefine timeline semantics; T037 is the behavioral authority.
- Do not add gesture coalescing/exact-settle policy; T042/T029 own scheduling.
- Do not add new timeline views, lanes, filters, or evidence versions.
- Do not rebuild scatter abstractions merely for symmetry.
- Do not block on full-grid readback during interactive events.

#### Blocked By

T013, T022, T023, T037.

#### Why It Is Blocked

Resident state needs normative analysis contracts, proven ABI/resource limits,
nonblocking ticket lifetimes, and the already-correct tactical timeline semantics.

#### Related Code

- `gpu_timeline_density.rs`, timeline packer/renderer, compute/render WGSL.
- Current `app_timeline.rs` resource creation/update path.
- T037 lane/range tests and T023 readback state machine.
- Scatter resident-state patterns that may inform but not dictate ownership.

#### Implementation Touchpoints

- Read first: every timeline buffer/pipeline/bind-group allocation, upload,
  readback, generation, and T037 mapping call site.
- Edit first: vertical timeline GPU state/config modules, then renderer/workbench
  adapters and obsolete per-update resource paths.
- Symbols to search: `TimelineDensityRenderer::new`, `dispatch_timeline_density`,
  `create_buffer`, `create_bind_group`, `update_density`, event upload, and poll.
- Required structural changes: private resident state, validated update request,
  explicit `Preview`/`Exact` field generation, and owned ticket registry.
- Do not edit: timeline semantic formulas, analysis selection, evidence, or final
  workbench coordinator policy.
- Verify in order: lifecycle/resource-reuse tests, T037 parity regressions,
  adapter-backed first/exact/cancel/device-generation tests, format, workspace.
- Stop and ask: if resident capacity requires silent truncation or a T037 semantic
  change, or if WGPU lifetime cannot be proven for a retired generation.

#### Implementation Details

```rust
pub struct TimelineDensityGpuState {
    dataset_generation: DatasetGeneration,
    device_generation: DeviceGeneration,
    event_buffer: wgpu::Buffer,
    event_count: u64,
    field_slots: [TimelineFieldSlot; 2],
    active_generation: Option<TimelineFieldGeneration>,
    pending: Option<TimelineUpdateTicket>,
}

pub enum TimelineUpdateQuality {
    Preview,
    Exact,
}
```

State construction validates T022's allocation/dispatch plan before creating any
resource. A dataset/device replacement prepares a complete new state and swaps it
only on success. View/cohort changes write bounded parameters/masks and dispatch
into an inactive slot; the prior active slot remains renderable until completion.

The engine returns a generation-tagged pending/ready result. Exact readback uses
T023 and never owns event-loop polling policy. Cancelled, timed-out, device-lost,
or stale results retire without publication. Stats say whether CPU counts/max are
current, pending, or unavailable; they never present stale values as exact.

#### Before / After

Before: timeline interaction recreates compute resources and synchronously waits
for mapped results.

After: dataset resources are resident, preview/exact work is generation-tagged,
and no engine update requires an interactive blocking readback.

#### Migration Notes

- Keep an explicit correctness wrapper for non-interactive tests/CLI if needed;
  interactive callers use start/progress/take-result.
- Migrate T037 formulas by call-through, not copied shader/host variants.
- Preserve the previous active generation when preparing/submitting a new one fails.

#### Misinterpretations To Prevent

- Wrong: cache only the pipeline. Correct: event/count/max/bind resources are
  dataset/device-resident and generation-owned.
- Wrong: mark submitted work active. Correct: publish only completed matching work.
- Wrong: change lane flips during extraction. Correct: reuse T037 exactly.

#### Invariants

- Event data uploads only for a new dataset/device generation or capacity rebuild.
- No interactive update blocks on GPU mapping.
- Active fields are complete and generation-matched; pending work is distinct.
- T037 lane/range semantics remain the sole behavioral contract.
- Failed/stale work cannot destroy the previous valid field.

#### Acceptance Criteria

- [ ] Resident timeline state reuses event/pipeline/binding resources across view
      updates and rebuilds only for validated generation/capacity changes.
- [ ] Preview/exact submission and completion are explicit and nonblocking.
- [ ] T037 mapping/parity regressions pass unchanged through the resident engine.
- [ ] Cancellation, timeout, stale generation, and device loss preserve prior state.
- [ ] Focused lifecycle, adapter-backed GPU, format, and workspace checks pass.

#### Testing Guidance

- Count resource creations/uploads through injected constructors; do not infer
  reuse from timing.
- Use deterministic completion injection and existing ignored adapter tests; no
  sleeps or smoke window.
- Keep T037 boundary vectors as the semantic oracle.
