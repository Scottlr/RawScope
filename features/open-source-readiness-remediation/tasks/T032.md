### T032 — Add Cross-Boundary Atomicity Regressions

#### Objective

Add a compact set of deterministic integration regressions proving that filtered
truth and multi-owner transitions stay consistent and old-or-new across the final
Rust/Python, analysis/render, controller, export, and GPU-boundary seams.

#### Scope

- Primary audit finding: RS-133.
- Add a shared deterministic fixture that produces an intentionally distinguishable
  old and new dataset/cohort/projection/selection/render generation.
- Prove filtered row-set identity/count/sample/aggregate/evidence consistency
  across analysis, linked views, controller publication, and export capture.
- Inject failure at each T041/T029/T030 candidate boundary and assert consumers
  observe the complete old or complete new generation, never a mixed tuple.
- Prove T021/T049 bundle/controller atomicity: partial formatting/IO, cancellation,
  stale completion, and closed-proxy/shutdown do not publish partial or false
  success state.
- Run the normative CPU/WGSL boundary vectors through actual pack/dispatch input
  contracts and existing opt-in adapter tests; keep host-only parity deterministic
  in normal CI.
- Reuse Rust/Python session/source compatibility vectors where a cross-language
  mismatch would create divergent accepted state.

#### Out of Scope

- Do not add property tests or fuzz targets; T051 owns that separate package.
- Do not benchmark latency/resources; T033/T057 own performance protocols.
- Do not create a live-window smoke harness, fake demo app, screenshot suite, or
  broad snapshot churn.
- Do not duplicate local unit tests already proving one owner in isolation.
- Do not weaken generation validation merely to simplify fixtures.

#### Blocked By

T003, T012, T017, T021, T024, T025, T030, T049, T050.

#### Why It Is Blocked

Cross-boundary tests must target final contracts and CI tiers; adding them before
the ownership/controller migrations would freeze temporary seams.

#### Related Code

- Existing integration tests under crate/app `tests/` and shared fixture patterns.
- T038/T041 filtered/atomic regressions, T029/T030 generation commits.
- T021 bundle failure seam, T049 export controller, T027 durable job completion.
- CPU/WGSL vectors and existing ignored adapter-backed GPU suites.
- Rust/Python session and source-adapter compatibility fixtures.

#### Implementation Touchpoints

- Read first: final public seams, existing fixture owners, CI GPU-tier policy, and
  every old-or-new invariant before deciding test placement.
- Edit first: small shared generation fixture under the narrowest existing test
  owner, then one table-driven suite per cross-boundary invariant.
- Symbols to search: generation tokens, `SelectionSnapshot`, active commit,
  bundle failure injection, export completion, parity vectors, and Python fixtures.
- Required structural changes: shared fixtures under `tests/common/` only where
  used by multiple integration tests; keep production files test-free.
- Do not edit: production behavior except a minimal injectable seam required to
  observe a real invariant; return to the owning task if behavior is wrong.
- Verify in order: focused suites by boundary, existing package tests, Python
  contract tests, opt-in GPU parity when available, format, workspace check.
- Stop and ask: if a proposed test needs a public API solely for inspection or
  requires nondeterministic timing/hardware in required CI.

#### Implementation Details

Use old/new fixtures with disjoint IDs/counts/labels so mixed state is impossible
to mistake for valid output. Each failure table names the stage, injected outcome,
expected active generation, pending cleanup, persistent error, and retry state.

For concurrency ordering, use fake executors, channels, barriers, and explicit
completion injection. Never sleep. Validate object identity/generation tuples and
semantic outputs rather than private field order.

Host CI checks exact CPU placement against WGSL-compatible declarative vectors and
host ABI packing. Existing adapter-backed tests run the same vectors on scheduled
hardware; they remain opt-in until T003 declares a runner.

#### Before / After

Before: local tests cover many components, but a fake/mixed cross-owner generation
or partial export can evade the suite.

After: a small high-signal regression layer fails if truth diverges or any
transactional boundary exposes mixed/partial state.

#### Migration Notes

- Move or reuse existing meaningful tests; do not duplicate assertions under a
  new filename merely to call them integration tests.
- Keep fixture schema stable and deterministic; update it only for intentional
  contract changes.
- Hardware absence is reported, not treated as semantic success.

#### Misinterpretations To Prevent

- Wrong: add hundreds of unit tests. Correct: prove the few realistic cross-owner
  failures identified by the report.
- Wrong: assert only no panic. Correct: assert exact old/new truth and cleanup.
- Wrong: make GPU tests mandatory on runners without adapters. Correct: required
  host parity plus scheduled adapter execution.

#### Invariants

- Filtered selection/evidence consumers share one row-set truth.
- A failed/stale transition exposes complete old state, never mixed state.
- A committed transition exposes one matching generation tuple.
- Bundle/export failure cannot appear as a complete successful report.
- Required tests are deterministic and do not depend on sleeps or a live window.

#### Acceptance Criteria

- [ ] Filtered truth is proven across analysis, linked views, active generation,
      evidence capture, and export.
- [ ] Failure tables prove old-or-new behavior for dataset/render/controller/UI
      and bundle/export commits.
- [ ] Stale/cancelled/proxy-closed completions preserve exact terminal/cleanup state.
- [ ] CPU/WGSL vectors run in host CI and the existing GPU tier consumes them.
- [ ] Rust/Python compatibility vectors remain aligned.
- [ ] Focused suites and required workspace checks pass without smoke artifacts.

#### Testing Guidance

- These tests are the deliverable; keep each name behavioral and each fixture
  bounded enough for normal CI.
- Prefer tables over copied cases and exact semantic assertions over snapshots.
- If a real bug appears, fix it in its owner rather than encoding the bug as gold.

- Risk: over-mocking can prove the test double rather than production; inject only
