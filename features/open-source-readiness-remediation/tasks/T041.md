### T041 — Make Current Demo Filter And Projection Updates Atomic

#### Objective

Repair current partial state commits for demo switches, filter/cohort uploads, and
scatter projections before controller reorganization by staging a complete next
state and applying it only after every fallible consumer succeeds.

#### Scope

- Primary audit findings: RS-111, RS-113, and RS-114.
- Add current-owner prepared mutation values for demo, filter, and projection
  changes across CPU state, GPU masks/points/fields, summaries, inspection,
  selection snapshot, UI/title, and export eligibility.
- Validate/build every next component without mutating active `WorkbenchApp`
  fields; make the final apply phase infallible and non-observable mid-swap.
- On any preparation failure, retain the entire previous state and persist a typed
  failure/retry status.
- Use T038's corrected selection snapshot for pending/active filter membership.

#### Out of Scope

- Do not move fields into final controllers; T050/T030 own structure.
- Do not add job/thread scheduling or change gesture cadence.
- Do not redesign UI controls, projections, or filters.
- Do not add new dataset formats or GPU resource sharing.

#### Blocked By

T005, T038.

#### Why It Is Blocked

Checked generations/selection truth are required so a prepared mutation can prove
all components describe the same state.

#### Related Code

- `demo.rs`, `app_scatter_filter.rs`, `app_scatter_projection.rs`, and dataset/
  timeline demo preparation.
- GPU mask/point/density resources and current filter/projection revisions.
- Summary/inspection/aggregate/selection/title/export state assignments.
- Existing filter/projection/demo workbench tests.

#### Implementation Touchpoints

- Read first: every active field written by each transition and all early returns/
  `?` after the first mutation.
- Edit first: focused prepared structs in the owning `app_*` modules, then replace
  direct mutation methods and add injected failure tests.
- Symbols to search: `switch_demo`, filter apply/reset, projection set, sequential
  `self.* =`, GPU upload/update, and error paths retaining partial values.
- Required structural changes: `PreparedDemoState`, `PreparedFilterState`, and
  `PreparedProjectionState` (or one coherent current mutation type if their fields
  genuinely coincide); no generic transaction framework.
- Do not edit: final controller layout, evidence wire, ingestion, or shader math.
- Verify in order: per-transition failure matrix, existing behavior tests, format,
  workspace check.
- Stop and ask: if any consumer is intentionally allowed to lag a generation or a
  transition cannot be prepared without mutating an external resource.

#### Implementation Details

Each request follows:

```rust
fn prepare_filter_change(
    &self,
    request: FilterRequest,
) -> Result<PreparedFilterState, WorkbenchOperationError>;

fn apply_filter_change(&mut self, prepared: PreparedFilterState) {
    // infallible moves only; no GPU/IO/allocation/callback
}
```

Prepared state owns all new resources/results and one generation tuple. GPU
resources are created/uploaded off to the side; active handles remain untouched.
Apply may replace one aggregate current-state field if introduced locally, or
perform consecutive infallible moves on the single owner thread with no callbacks;
no fallible operation occurs after the first move. T030 later replaces this with
one aggregate `Arc` swap.

Demo failure must preserve mode/dataset/render/UI together. Filter/projection
failure preserves prior CPU mask/points, all GPU consumers, summaries, selection,
and title/export context. Error remains visible until retry/dismissal.

#### Before / After

Before: demo/filter/projection updates can commit some consumers and leave others
on the prior revision.

After: each current transition is complete old or complete new, with a typed
persistent failure on preparation error.

#### Migration Notes

- T050 moves these prepared commands into controllers; T030 replaces apply with a
  single aggregate active-generation swap. Preserve failure matrices.
- Do not leave both direct and prepared transition paths callable.

#### Misinterpretations To Prevent

- Wrong: clone current state, mutate `self`, then restore on error. Correct: never
  touch active state until all fallible work succeeds.
- Wrong: update CPU first and “eventually” GPU. Correct: same generation commits to
  every required consumer.
- Wrong: clear error/status on redraw. Correct: persistent typed failure.

#### Invariants

- Preparation has no active-state side effects.
- Apply is infallible and generation-complete.
- Failure leaves all active fields/resources/revisions unchanged.
- Selection/filter/GPU/title/export state share one generation after commit.

#### Acceptance Criteria

- [ ] Demo/filter/projection use prepared values and infallible apply.
- [ ] Injected failure at every preparation stage preserves exact old state.
- [ ] Success updates every named consumer to one generation.
- [ ] Persistent typed failure/retry state replaces silent partial retention.
- [ ] Focused workbench tests, format, and workspace check pass.

#### Testing Guidance

- Inject the second/late consumer failure for CPU, GPU, summary, selection, and UI
  preparation; assert every active generation/handle remains old.
- No live GPU is required for transaction tests; use an injected resource factory.
- No window/screenshot smoke tests.

#### Agent Handoff Context

This is a behavioral repair, not the controller refactor. T050/T030 must move the
prepared semantics intact rather than reintroduce sequential active mutation.

## Final Notes

- Recommended order: inventory writes, filter, projection, demo, persistent errors,
  failure matrix.
- Human review: whether any optional consumer may degrade rather than block commit.
- Risk: hidden side effects inside existing GPU update methods must be replaced by
  side-effect-free resource preparation.
