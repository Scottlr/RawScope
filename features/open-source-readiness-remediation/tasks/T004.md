### T004 — Publish Contributor Security And Release Governance

#### Objective

Give external users and contributors a complete public operating contract for
development, conduct, vulnerability disclosure, support, versioning, and release
approval without exposing agent-only instructions as project governance.

#### Scope

- Primary audit finding: RS-011; establishes governance prerequisites for the
  release-engineering finding completed by T056.
- Add `CONTRIBUTING.md`, `SECURITY.md`, `CODE_OF_CONDUCT.md`, support/versioning
  policy, `CHANGELOG.md`, issue forms, and pull-request template.
- Document exact contributor prerequisites and commands from T002/T003, crate
  ownership boundaries, meaningful-test policy, and performance-claim policy.
- Define evidence/session schema compatibility and deprecation rules.
- Define a release checklist and roles; T035 will automate the approved steps.

#### Out of Scope

- Do not invent a private email address, response SLA, signing identity, or
  maintainer role.
- Do not create workflows, publish releases, or modify product code.
- Do not copy the full `AGENTS.md` or `.codex/skills` content into public docs.
- Do not promise semantic versioning guarantees broader than approved APIs.

#### Blocked By

T002, T003.

#### Why It Is Blocked

Public commands and required-check names must come from the accepted toolchain/
policy and working CI. Security contact, conduct text, support channels, and
release authority also require maintainer approval before completion.

#### Related Code

- `AGENTS.md` and `docs/AGENTS.md` — private agent rules that inform but do not
  replace public governance.
- `README.md`, `docs/ARCHITECTURE.md`, `docs/BENCHMARKS.md`, and schema docs.
- Missing root contribution/security/conduct/changelog/support/release files.
- Missing `.github/ISSUE_TEMPLATE/` and `.github/pull_request_template.md`.

#### Implementation Touchpoints

- Read first: existing public docs, T002/T003 command names if already landed,
  and maintainer-approved contact/roles.
- Edit first: `CONTRIBUTING.md`, `SECURITY.md`, then templates and release policy.
- Symbols/topics to search: `cargo fmt`, `clippy`, `evidence`, `schema version`,
  `benchmark`, `non-goal`, and `Current Next Task`.
- Required structural changes: typed issue forms for bug, correctness/evidence,
  performance, and feature requests; one PR checklist tied to actual gates.
- Do not edit: source, manifests, lockfiles, generated artifacts, or old feature
  task completion records.
- Verify in order: link/path review, template rendering, command consistency with
  current repo, and human approval of contact/conduct/release text.
- Stop and ask: for security contact, response expectations, code-of-conduct
  choice/enforcement address, release approvers, and versioning promises.

#### Implementation Details

`CONTRIBUTING.md` must cover setup, branch/PR flow, exact local checks, focused
test expectations, crate ownership, file-size/module rules, and how to report
benchmark evidence. It must be usable without Codex.

`SECURITY.md` must cover supported versions, private disclosure channel,
information requested, coordinated disclosure handling, and explicit exclusion
of public issues for unpatched vulnerabilities. Never put placeholder contacts
in a merged policy.

The version/release policy must distinguish:

- Rust API compatibility;
- evidence wire-version compatibility and legacy readers;
- session manifest compatibility;
- Python SDK compatibility;
- native binary/platform support.

`CHANGELOG.md` should use an approved human-readable format with `Unreleased`.
The release checklist names approval, CI, package inspection, schema compatibility,
SBOM/provenance, artifact test, signing (if approved), announcement, and rollback.

#### Before / After

Before: external contributors have no supported workflow or disclosure/release
contract.

After: public documents and templates accurately route contributions and risks,
and T035 has an approved release process to automate.

#### Migration Notes

- Link governance from `README.md` without rewriting product claims (T034 owns
  the larger README reconciliation).
- Consume the final T002/T003 command and job names; do not merge placeholders or
  references to future task IDs as if they were contributor instructions.

#### Misinterpretations To Prevent

- Wrong: copy agent instructions verbatim. Correct: write concise public policy
  for humans and ordinary tooling.
- Wrong: leave `security@example.com`. Correct: stop until an approved channel
  exists.
- Wrong: call every internal type semver-stable. Correct: define the supported
  public surface explicitly.

#### Invariants

- No placeholder contact or unapproved legal/conduct text is merged.
- Public check commands match repository gates.
- Schema compatibility policy names evidence and session contracts separately.
- Templates ask for reproducible evidence without requesting secrets/datasets.

#### Acceptance Criteria

- [ ] Contribution, security, conduct, support/versioning, changelog, and release
      policy documents exist and are linked.
- [ ] Issue and PR templates reflect actual ownership and check requirements.
- [ ] Approved disclosure/release contacts and roles are present.
- [ ] No private agent-only path is required to contribute successfully.

#### Testing Guidance

- No Rust/Python tests are required for documentation/template-only changes.
- Verify every relative link and every command against the then-current repo.
- Do not add a doc smoke script or fake issue.

#### Agent Handoff Context

Keep this public, terse, and truthful. T035 implements the release workflow;
T034 later reconciles architecture/API/product documentation with final code.

## Final Notes

- Recommended order: contribution/security decisions, templates, versioning,
  changelog/release checklist, README links.
- Human review is mandatory for all contact, conduct, and release authority text.
- Risk: governance becomes stale if T003 job names change without updating it.
