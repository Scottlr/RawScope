### T014 - Add Closed Mode Compatibility And Generic Workbench Controls

#### Objective

Integrate the shipped visual-field modes into one mapping-driven workbench
controller and a compact production-grade control surface, removing profile-
identity branches and superseded scatter-only UI/state owners.

#### Scope

- Consume T001's one analysis-owned mapping compatibility rule and add one
  workbench-owned availability function for cohort state, device/resource
  capability, and derived-field readiness.
- Migrate the final scatter controller/state into a generic visual-field
  controller that owns mapping, mode, presentation, and generation-tagged
  commands without reproducing render resources.
- Expose density, category composition, cohort comparison, and density ridges
  only when their typed prerequisites are present; represent preparing and
  unavailable states explicitly.
- Integrate time-value mapping into the same field/mode controls while keeping
  the discrete-lane timeline as a distinct view.
- Keep the existing typed filter/cohort controller as the sole row-membership
  owner. Project its active summary/clear/edit actions into the refined surface,
  and invalidate visual generations by cohort identity rather than rebuilding a
  UI-owned mask.
- Split oversized visual-encoding/UI owners by user responsibility: field
  mapping, mode/presentation controls, legend, and inspection projection.
- Replace dataset-profile identity checks for axis labels/guides/availability
  with typed schema kinds plus optional generic formatting/guide hints.
- Refine control hierarchy, spacing, labels, focus/hover/disabled states,
  keyboard navigation, contrast, and reduced-motion transitions.
- Show a concise dataset display name in the primary chrome; keep a full source
  path for local files, or the existing redacted source display for other URI
  kinds, in an explicit dataset-details action rather than the visual panel.

#### Out of Scope

- No plugin mode registry, generic inspector framework, chart grammar, ECS,
  trait-object controller graph, arbitrary mode combinations, or user-authored
  shaders/palettes.
- No profile-specific control, label, mode, or visual branch.
- No tutorial copy, marketing panel, second shell redesign, or new UI framework;
  consume T018's landed workspace regions and theme tokens.
- No session/evidence serialization in workbench state.
- No aesthetic control that mutates analytical counts or row membership.
- No second filter editor/model hidden inside composition layer selection;
  choosing visible category layers does not filter rows.

#### Implementation Details

Use T001's `VisualFieldMapping::supports(mode)` as the only stable mapping
compatibility rule. Keep device, budget, cohort, and readiness availability in
the workbench controller domain, without dynamic registration:

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum ComparisonCohortState {
    Missing,
    Empty,
    Ready,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum VisualModeUnavailableReason {
    ProjectionIncompatible,
    CategoryNotMapped,
    ComparisonCohortMissing,
    ComparisonCohortEmpty,
    DeviceLimit,
    ResourceBudget,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum VisualModeAvailability {
    Available,
    Preparing,
    Unavailable(VisualModeUnavailableReason),
}

pub fn visual_mode_availability(
    mode: VisualFieldMode,
    mapping: &VisualFieldMapping,
    comparison: ComparisonCohortState,
    capabilities: VisualFieldCapabilities,
    readiness: VisualFieldReadiness,
) -> VisualModeAvailability;
```

The closed compatibility table is:

| Projection | Density | Composition | Comparison | Ridges |
|---|---|---|---|---|
| Numeric pair | Yes | With category | With baseline | Yes |
| Time-value | Yes | With category | With baseline | Yes |
| Discrete-lane timeline | Existing timeline modes only | No | Existing behavior only | No |

Device/resource failure can make a derived mode unavailable, but the base exact
density path must retain its documented fallback. `Preparing` keeps the last
compatible settled presentation visible with a clear freshness state.

Use typed commands:

```rust
pub enum VisualFieldCommand {
    SetMapping(VisualFieldMapping),
    SetMode(VisualFieldMode),
    SetDensityPresentation(DensityPresentation),
    SetComparisonPresentation(ComparisonPresentation),
    SetComparisonSplit(ComparisonSplit),
    SetRidgeScale(RidgeScale),
}
```

The controller validates commands, updates canonical state once, and submits a
new coordinator intent only when the resource-producing intent key changes.
Palette/legend or split-uniform changes stay presentation-only where possible.
No egui closure mutates renderer resources directly.

Mode controls use a compact segmented/menu hierarchy appropriate to the number
of choices, familiar icons from the existing icon set where available, and
short tooltips for unfamiliar controls. Disabled choices remain discoverable
with a precise reason. Legends are mode-specific projections of shared palette
and formula state, not independently authored swatches/text.

Axis semantics derive from `VisualAxisDomain`, store column kind, field display
name/unit hints, and optional profile hints. Integer columns get integer ticks;
timestamps get timestamp ticks; continuous numeric fields use finite numeric
formatting. A profile may suggest defaults but cannot unlock a mode or select a
different formula.

#### Before / After

**Before:** scatter-specific state, profile branches, and a growing encoding
panel make new modes feel attached rather than native.

**After:** one generic controller and closed compatibility table make every mode
behave consistently, while focused controls expose only meaningful choices and
keep source-path detail out of the primary visual hierarchy.

#### Migration Notes

- Preserve current shortcuts, pan/zoom/hover/crosshair/tooltip/pin behavior where
  the action remains meaningful.
- Convert persisted legacy scatter view state through T015 adapters; do not keep
  two live controllers.
- Remove profile identity checks only after equivalent typed hints/defaults are
  available; do not discard useful formatting behavior.
- Renames should follow the landed remediation module layout, with thin facades
  and intentional `pub use` only.

#### Misinterpretations To Prevent

- Wrong interpretation: every mode can combine with every other mode. Correct
  rule: one closed primary mode and its bounded presentations are supported.
- Wrong interpretation: disabled means silently broken. Correct rule: expose a
  precise typed unavailable/preparing reason.
- Wrong interpretation: generic means a plugin API. Correct rule: the product
  supports a curated enum and explicit matrix.
- Wrong interpretation: hiding the source path hides provenance. Correct rule:
  full provenance remains one explicit details action and in evidence.

#### Invariants

- One controller state is authoritative for mapping/mode/presentation.
- UI actions emit typed commands and never mutate render resources directly.
- Equivalent commands are idempotent and do not schedule duplicate generation.
- Availability depends on typed capability/state, never dataset profile identity.
- Every enabled choice has a complete compute/presentation/inspection path.
- Source provenance remains accessible without dominating visual controls.
- Keyboard, focus, contrast, disabled, and reduced-motion states remain usable.
- Mixed files over roughly 400 lines are split by responsibility before growth.

## Final Notes

- Recommended order: compatibility function, controller migration, typed command
  projection, profile-neutral axes, focused UI split, interaction curation.
- Unresolved questions: final mode ordering, exact compact control pattern, and
  whether the dataset-details action belongs in top bar or dataset panel.
- Risk: too many visible controls can make a curated instrument feel like a
  shader playground; progressive disclosure must follow the mode matrix.
- Human review: production-grade hierarchy/accessibility on normal and narrow
  windows, without accepting visual-only controls that lack real behavior.
